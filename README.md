# MashaBot

Запуск двух сервисов сразу:
- `masha-bot` (Java Telegram bot)
- `yt-video-analyzer` (Python FastAPI для анализа YouTube по субтитрам)

## Быстрый старт

```bash
cp .env.example .env
# заполни обязательные ключи в .env

docker compose up -d --build
```

Проверка:
```bash
docker compose ps
docker logs -f masha-bot
docker logs -f yt-video-analyzer
```

Остановить:
```bash
docker compose down
```

## Важные переменные

- `TG_BOT_TOKEN` — токен Telegram бота
- `OPENAI_API_KEY` — ключ для Java-бота (OpenRouter/OpenAI-совместимый)
- `OPENROUTER_API_KEY` — ключ для `yt-video-analyzer`
- `VIDEO_ANALYZER_URL` — URL Python-сервиса для Java-бота (по умолчанию `http://yt-video-analyzer:8000/analyze`)

## Обработка запросов и диагностика

Сообщения одного диалога (чат + пользователь) выполняются по порядку, разные диалоги — параллельно, в том числе для разных участников одной группы. Если отправитель неизвестен, очередь общая для таких сообщений чата. По умолчанию работают 4 обработчика; лимит составляет 64 принятых сообщения, включая выполняемые, и 8 сообщений на диалог. Переменные: `BOT_WORKERS`, `BOT_QUEUE_CAPACITY`, `BOT_DIALOG_QUEUE_CAPACITY`. При перегрузке бот пытается отправить просьбу повторить сообщение; если очередь уведомлений тоже заполнена, отказ фиксируется в логах. Старый p-bot дополнительно сохраняет общий контекст чата и последовательно обновляет его; обычные GPT-диалоги от него не зависят.

Сводки долговременной памяти формируются отдельно, одним фоновым обработчиком. Его лимит — `BOT_SUMMARY_QUEUE_CAPACITY` (по умолчанию 16). Не принятая или неудавшаяся сводка повторно планируется при следующем успешном обмене сообщениями. Завершение старой сводки не удаляет новые сообщения. Очереди и короткая история хранятся в RAM и не переживают перезапуск; сохранённые файлы памяти остаются в volume.

Во время обработки обновляется статус «печатает». Он отправляется отдельно и не задерживает основной ответ. Пустой ответ модели и ошибка обработки приводят к понятному сообщению пользователю, если Telegram принимает отправку. История обновляется после успешной отправки ответа.

Текстовые отправки в Telegram повторяются не более 3 раз для явных ответов 429/5xx. Для 429 учитывается `retry_after`; если пауза больше 10 секунд или отсутствует, отправка завершается ошибкой, чтобы надолго не занимать обработчик. Неопределённые транспортные ошибки автоматически не повторяются: сообщение уже могло быть доставлено. При исчерпании попыток ошибка остаётся в логах и отправляется в `ERROR_CHAT_ID`, если он настроен и отправка уведомления доступна. Уведомления содержат номер запроса и тип ошибки, без тела ответа API или переписки.

GPT ограничен `CHATGPT_TIMEOUT_SEC` на чтение и этим значением +10 секунд на полный вызов. Анализ видео ограничен `VIDEO_ANALYZER_TIMEOUT_SEC` (по умолчанию 90 секунд); его read timeout согласован с общим лимитом. Для старого p-bot, ЦБ и синтеза речи заданы connect/read timeouts 10/30 секунд. При 4 занятых обработчиках и дополнительных сообщениях в очереди ожидание всё ещё возможно — размер очереди и длительность API видны в диагностике.

Логи содержат события `message_started` (`queue_ms`), `handler_selected`, `gpt_finished`, `video_finished`, `telegram_send`, `message_finished`, а также `queue_rejected`, `summary_failed`, `telegram_retry`. Поле `request`/MDC связывает этапы с update ID Telegram. Тексты запросов, токены и тела ошибок внешнего API в этих событиях не записываются.

```bash
mvn -B -ntp verify
docker build -t masha-bot:local .
```

Тесты используют локальный HTTP-сервер и mock Telegram/GPT, рабочие ключи им не нужны. Dockerfile запускает тесты до упаковки. В текущем Compose у Java-сервиса указан готовый `image`, поэтому `docker compose up --build` не собирает его из изменённых исходников: для локальной проверки нужно явно использовать собранный образ. Публикацию образа и замену работающего контейнера выполняют отдельно, после резервного копирования конфигурации и памяти. Не запускайте вторую копию с тем же рабочим токеном для тестирования.
